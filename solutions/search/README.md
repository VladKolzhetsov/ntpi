# Search-пайплайн

Полный цикл search-задач: вопрос по базе знаний → `answer.txt`. Построен по общему принципу харнесса — **максимум детерминизма, LLM только там, где без неё нельзя**: единственный платный шаг основного пути — один вызов
планировщика (~114–141 output-экв. на задачу).

```
task.json
   │  extract_question (детерминированно)
   ▼
вопрос + kb/*.md ──► KnowledgeBase (парсинг, индексы, граф имён)
   │                       │
   │                       └─ is_healthy? ── нет ──────────────┐
   ▼                                                          │
SearchPlanner ──► unanswerable ──► СДАЛИСЬ (файл не создаём)   │
   │  (LLM: 1 вызов + ≤1 ремонт)                              │
   ▼                                                          │
Plan (DSL: find/get/match/count)                              │
   ▼                                                          │
executor.execute (детерминированно) ── None/сбой ─────────────┤
   │                                                          ▼
   │                                          Fallback: single-shot QA
   │                                          по компактному дампу базы
   │                                          (LLM, NOT_FOUND → сдаёмся)
   ▼
answer.txt — в ОБОИХ позициях: <task_dir>/answer.txt и
             <task_dir>/workspace/answer.txt
```

## Компоненты (`v2/` — текущая)

Версия — самодостаточный срез пайплайна: `solutions/search/v2/` (была `v1/`,
переключена 2026-11-13). Общий каркас версий такой же, как у остальных
типов (`solutions/<type>/<version>/solver.py::solve`), поэтому диспетчер
(`solutions/runner.py`) не имеет спец-случаев.

| Файл | Роль | LLM |
|---|---|---|
| `v2/kb.py` | `Node` + `KnowledgeBase`: парсинг карточек, поиск, граф имён | — |
| `v2/planner.py` | вопрос + схема → компактный JSON-план в DSL | 1 вызов + ≤1 ремонт |
| `v2/executor.py` | исполнение плана обходом базы | — |
| `v2/solver.py` | сборка лестницы, адаптивный кап, fallback-QA, ответ | fallback: 1 вызов |
| `v2/complexity.py` | оценка глубины + `cost_worst` (калибровка) | — |

| Версия | Точность (live) | Стоимость |
|---|---|---|
| `v1` | 18/24 verified (baseline), не решает 14-хоповые (кап 250) | 2882.8 экв. на 24 |
| `v2` (текущая) | 18/24 verified на том же пересечении, `0034` (14 хопов) 3/3 | 2455.1 экв. на 24 (−15%) |

Почему v2 по умолчанию: та же точность на пересечении, −15% расход,
решает длинные вопросы (`search_0034`: v1 не влезает в кап 250, v2 — 309.5
экв. за 5 баллов) и публикует `cost_worst` для worst-case триажа раннера
(нормировка `EXPECTED_COST × worst / median` — см. `solutions/runner.py`,
живая реплика A/B: 2026-11-13, 551.3 экв. / 18 балл. = эффект +6.7%).
`v1` доступна: `--versions search=v1`.

Вспомогательные (общие для всех типов задач, живут в `solutions/`):

- `question.py` — `extract_question`: срез инструкции до последнего `?`;
- `task_parser.py` — `Task.from_dir()`, `answer_candidates` (обе позиции
  answer.txt), `read_answer()`;
- `llm.py` — `LLMClient` + `BudgetTracker`, opportunistic json-режим;
- `planning.py` — `compile_text` (temp 0, кап max_tokens) и `extract_json`.

## kb.py — база знаний

`Node.from_file()` разбирает один markdown-файл (карточку сущности):

```markdown
# Irina Sato              ← каноническое имя
- Born: 1983              ← поле "Born" = "1983"
- Employer: Fjord Data    ← значение-ссылка на другую сущность
```

- **тип сущности** — префикс имени файла (`person_irina_sato.md` → `person`);
- допускаются буллеты `-`/`*` и строки без них; строки без `Key: value`
  считаются мусором (`garbage_lines`); карточка без единого поля — `None`;
- `get(field)` — точное совпадение ключа, затем casefold;
- `aliases()` — имя из заголовка + стем файла без префикса типа.

`KnowledgeBase.from_dir()` рекурсивно обходит каталог (скрытые файлы
`._*`, `.git/` — мимо) и строит индексы:

- `find(name)` — ноды по имени/алиасу (нормализация регистра и пробелов);
  **коллизия имён → список** — вызывающий решает, что делать;
- `find_in_text(text)` — ноды, упомянутые в тексте; сначала самые длинные
  совпадения (более специфичные имена);
- `match(field, value, type=)` — обратный поиск: все ноды, у которых поле
  равно значению («какие компании headquartered in Osaka»);
- `resolve(value, prefer_type=)` — значение-ссылка → нода; ребро графа.
  Однозначно → нода; однозначно в рамках типа → нода; иначе `None`;
- `schema()` — `{type: [поля]}` — компактное описание базы для промпта.
  **Размер O(число типов × полей), а не O(карточек)**;
- `is_healthy()` — распарсилось ли ≥ 50% файлов; иначе формат чужой →
  solver сразу идёт в fallback, минуя планировщик.

Графа как структуры нет: «рёбра» — это значения-имена в полях, резолвящиеся через `resolve()` по пересечению имён. Так многохоповые вопросы (person → Employer → Headquarters) становятся цепочкой `get`-шагов.

## planner.py — планировщик

`SearchPlanner.plan(question, kb) -> PlanOutcome` — **единственный платный
шаг основного пути**:

1. системный промпт (~400 ток.): описание DSL, правила «не выдумывай поля
   и значения», пример карточки и пример плана;
2. пользовательский: `kb.schema()` + вопрос;
3. один вызов LLM (temp 0, `max_tokens=250`, json-режим
   `response_format: json_object` — opportunistic: при HTTP 400 клиент
   повторяет без него и отключает до конца сессии);
4. `extract_json` → `validate_plan` — строгая валидация против схемы:
   допустимые ops, канонизация регистра полей и типов по схеме (**авто-фикс
   самого частого класса ошибок — без ремонтного вызова**), корректность
   ссылок на переменные, число в `match.value` → str;
5. при невалидном плане — **один ремонтный раунд**: модель видит свой
   ответ и короткую ошибку, отвечает исправленным планом.

Контракты: `Step(var, op, args)` / `Plan(steps, answer)` /
`PlanOutcome(plan, unanswerable, error)`.

Имена сущностей **не** валидируются против базы: планировщик их не видит
(промпт O(1) от размера базы) и копирует из вопроса как есть. Правильность
линкинга — забота executor'а.

### DSL плана

```json
{"steps": [
  {"var": "p", "op": "find", "name": "Sergei Garcia"},
  {"var": "e", "op": "get", "from": "p", "field": "Employer"},
  {"var": "h", "op": "get", "from": "e", "field": "Headquarters"}],
 "answer": "h"}
```

| op | Аргументы | Возвращает |
|---|---|---|
| `find` | `name`, `type` (опц.) | нода; ≠1 совпадение → провал шага |
| `get` | `from`, `field` | поле; значение-имя **авто-резолвится в ноду** — отсюда многохоповость |
| `match` | `type`, `field`, `value` | список нод с равным значением поля (обратный поиск) |
| `count` | `from` | размер списка из `match`-шага |

Невыполнимость уровня **схемы** (нужного поля нет ни у одного типа) →
планировщик отвечает `{"unanswerable": true}`. Невыполнимость уровня
**данных** (сущность не найдена, неоднозначность, пустой match) →
executor возвращает `None` → fallback.

## executor.py — исполнитель

`execute(plan, kb) -> str | None` — детерминированный обход, без LLM:

- шаги исполняются по порядку, результаты связываются переменными;
- `find` требует ровно одного совпадения (после опциональной фильтрации по
  типу); ноль или неоднозначность → `None`;
- `get` авто-резолвит значение-имя в ноду (`_as_node`) — так из цепочки
  шагов возникает обход графа; значение не-имя остаётся скаляром;
- `match` → список; `count` → `len`;
- форматирование ответа, вербатим из базы: нода → каноническое имя,
  скаляр → `str`, список → имена через `", "`, число → `str(int)`.

Любая неудача = `None` = «звонок в fallback». Никаких догадок.

## solver.py — сборка

`solve(task, client, model) -> SolveResult`:

```python
@dataclass
class SolveResult:
    task_id: str
    status: str        # "answered" | "unanswerable" | "failed"
    answer: str | None
    written: list[Path]    # реально созданные answer.txt
    cost: float            # дельта BudgetTracker на этой задаче
    trace: list[str]       # ступени: "plan: 3 steps", "executor: no answer"...
```

Лестница:

1. `extract_question` → `KnowledgeBase.from_dir(workspace/kb)`;
2. `is_healthy()`? — нет → сразу fallback (планировщик не вызываем);
3. `plan()`: `unanswerable` → **сдаёмся, файл не создаём**;
4. `execute()`: ответ → запись; `None`/исключение → fallback;
5. **fallback** — single-shot QA по компактному дампу всей базы:
   одна строка на карточку `person: Irina Sato | Born=1983, ...`.
   Модель видит все имена — то есть сама решает задачу линкинга, на которой
   обычно и спотыкается план. Ответ `NOT_FOUND` → сдаёмся. Дамп больше
   **400 нод** → fallback не вызываем (промпт O(размер базы); BM25-отбор
   добавим, если появятся большие базы).

Ответ пишется в **обе** позиции — `<task_dir>/answer.txt` и
`<task_dir>/workspace/answer.txt` (регламент и инструкция задачи
расходятся в том, где его искать) — с `\n` на конце (семантика `echo`).
При `unanswerable` и полном провале лестницы файл **не создаём**:
мусорный ответ гарантированно провалит проверку, а «нет файла» не
портит статистику ложными попытками.

## Измеренная стоимость (живой прокси)

| Путь | Вызовы LLM | Output-экв. |
|---|---|---|
| план-путь, однофактовый вопрос | 1 | 113.8 |
| план-путь, two-hop | 1 | 135.1–141.1 |
| план + 1 ремонт | 2 | ~230 |
| fallback-QA (база 38 карточек) | +1 | ~90–110 |

Эквивалент = `completion_tokens + prompt_tokens / 10`. Живой e2e на
тренировке (search_0001, search_0005): 6/6 прогонов верны, все — одним
вызовом, fallback не понадобился.
