## Полная стоимость отдельно

В 81 запуске задач: 3 без LLM (пустая KB), 78 с первым вызовом;
14/78 (17.95%) потребовали последующих вызовов. Средняя добавочная
стоимость по всем 78 — 8.08 экв. Эти цифры зависят от состава корпуса,
не добавлены автоматически к каждому прогнозу. В частности search_0033
получила верный ответ лишь в 1/3 повторов калибровки, search_0029 выдаёт
ответ при противоречивых карточках. Точность стоимости не равна точности решения.

Константы runner не менялись. Адаптивный max_tokens использует output-прогноз
с запасом: +30% при confidence>=0.6, иначе +60%, затем +16 токенов,
минимум 100, округление вверх до 32. Для unknown минимум 400.
Перед каждым вызовом из remaining вычитается input estimate с запасом 10%.
Кап сокращается только если остаётся хотя бы predicted output; иначе план
не запрашивается. Это мягкая оценка, не точный tokenizer и не глобальная
атомарная резервация между воркерами.

## cost_worst: верхняя граница полной стоимости задачи

Детерминированная оценка ДО первого вызова (0 токенов), поле
`SearchComplexity.cost_worst`. Считает худший путь лестницы solver:
план → ремонт → fallback QA. Не ожидание и не интервал: вероятности
не нужны (P(ветки)<=1), перенос калибровки с тренировки не нужен —
лестница конечна по коду, каждый completion ограничен нашим max_tokens,
дамп KB вычислим без LLM.

```text
C_plan    = input/10 + cap                       (completion <= max_tokens по API)
C_repair  = max(C_sem, C_trunc)                  (ветки взаимоисключающие)
C_sem     = (input + echo + err)/10 + cap        (эхо ответа + хвост ошибки валидации)
C_trunc   = (input + 30)/10 + trunc_cap          (приписка + удвоенный кап,
                                                  округление ((cap*2+31)//32)*32 как в planner)
C_fallback= qa_input/10 + 60                     (QA-промпт: system + вопрос + дамп KB)
cost_worst= C_plan + C_repair + C_fallback
```

Константы (complexity.py): `echo = min(cap, 500)` — обрезка ответа в
ремонтном промпте `text[:2000]`; `err = 60` — хвост «Invalid plan: …
known fields: …», зависит от схемы, с запасом; `30` — приписка о
перегенерации; `60` — output-кап QA (зеркалит `_fallback_qa` в solver).
Гейты solver отражены в формуле: пустая KB или `len(kb) > MAX_FALLBACK_CARDS`
→ C_fallback = 0; при `kb=None` (юнит-контексты без базы) слагаемое
не оценивается, в reasons пишется причина.

Единственная оценка внутри — перевод символ→токен для input (MAPE 0.58%,
максимум 3.34% LOO): это ~0.5% от cost_worst, отдельного запаса не введено.
Не входит: json-режимный 400-зонд и сетевые ретраи (usage не возникает),
бюджетный гейт (только сокращает трату). При unanswerable фактический
расход ниже — граница остаётся корректной.

Числа (live): steps=2, KB 18 нод → ~593; steps=5 → ~682; steps=14
(cap 352) → ~1296; unknown-структура (cap 400) → ~1409; KB 450 нод
(QA закрыт гейтом) → ~493. Оси вариации — steps через cap и размер KB
через дамп: граница не константа.

Валидация против всех сохранённых v2-прогонов (A/B капов + компактные
серии + калибровка): 262 слота по 27 задачам, нарушений 0. Максимум
фактического к границе — 0.35 (search_0033 с QA, actual_max 237.3 при
worst 681.8); самый дорогой слот прогона — search_0034: 425.3 при
worst 1296.4 (0.33, старая конфигурация капа). Типичный медианный слот
~0.16 границы. Юнит-покрытие — `solutions/search/test_v2_cost_worst.py`
(разложение формулы, инварианты, монотонность по steps/KB, гейты).

## Подключение к раннеру

Солвер публикует границу через `cost_worst(task)` в модуле солвера
(search/v2 — единственный). Раннер (флаг `--worst-case`,
`RunConfig.worst_case`, по умолчанию выключен) применяет её к плотности
`reward / cost_worst` и envelope = `cost_worst` без CAP_FACTOR; задачи
без границы сортируются и капаются по типовому профилю, т.е. без флага
поведение прежнее. На корпусе 122 задач флаг опускает search-задачи на
24–80 позиций (знаменатель 493–1443 вместо 140): в дефиците бюджета
дорогие по границе задачи уходят в хвост.
