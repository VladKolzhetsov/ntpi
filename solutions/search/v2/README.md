# Search v2: компактный план и оценка глубины

Независимая копия v1 (2026-11-11): kb, executor, planner, solver, complexity.
Внутренние импорты ведут в v2. Выбор через `--versions search=v2`.

## Изменения

- Planner требует однострочный JSON без пробелов вне строк. Все примеры DSL
  тоже компактные. Уточнено: переходы по ссылкам — get; match.value — литерал.
- Solver вычисляет адаптивный cap; `MAX_PLAN_TOKENS = 400` остаётся дефолтом
  при отдельном вызове конструктора planner. `solve(..., max_tokens=400)`
  переопределяет рекомендацию, но также проходит бюджетный гейт.
- Complexity распознаёт сокращение `main/primary road → road`, отмечая
  неоднозначность, если сокращению соответствуют несколько полей схемы.
- `Which city did ... arrive from?`: city — тип ответа, а `arrive from` —
  отношение Arrived from. Повторное City внутри вложенной цепочки сохраняется.
- От единственного якоря проверяются пути, покрывающие ВСЕ распознанные
  отношения с их кратностью. Это не выбор кратчайшего пути. Возвращаются
  `relation_path` и `graph_status`: unique / ambiguous / no_path / limit /
  not_checked. Ограничения: 2000 состояний, глубина 64. Циклы конечны за счёт
  расходования упоминаний полей. Неоднозначные ссылки не разрешаются догадкой.

Это оценщик, не общий семантический разбор: пути, требующие полностью
неупомянутых отношений, он пока не достраивает. Порядок отношений в вопросе
не доказывается графом. Прогноз стоимости теперь считается по отдельным
input/output-компонентам (tokens.py, CALIBRATION.md). Результат complexity
добавляет predicted_input_tokens, predicted_output_tokens,
recommended_max_tokens. Solver передаёт cap в planner и пишет прогноз в trace.
Приоритет runner остаётся прежним.

Помимо первого вызова complexity считает `cost_worst` — детерминированную
верхнюю границу ПОЛНОЙ стоимости задачи (план + ремонт + fallback QA,
формула и live-валидация в CALIBRATION.md). Считается до первого вызова из
наших же промптов, капов и дампа KB; вероятности не нужны. Появляется в
trace солвера как `worst≈…`.

Раннер подключает границу через контракт `cost_worst(task)` этого модуля:
флаг `--worst-case` (RunConfig.worst_case, офлайн по умолчанию) даёт
плотность `reward / cost_worst` и envelope = `cost_worst` без CAP_FACTOR
(граница уже покрывает всю лестницу). Без хука или с ошибкой — типовой
профиль EXPECTED_COST, т.е. режим офлайн сохраняет прежнее поведение
бит-в-бит.

Planner читает finish_reason из raw-ответа через compile_response. `length`
означает усечение; без этого поля признак — невалидный JSON при output>=cap.
Усечение увеличивает cap вдвое в пределах существующего max_repairs и бюджета.
Оборванный JSON в повтор не передаётся. Семантическая ошибка ремонтируется
обычным способом. QA тоже проверяет наличие бюджета перед вызовом.

## Проверки и результаты

`solutions/search/test_v2.py`: 8 тестов — тренировочные цепочки 4/5/14 шагов,
повторения/циклы, неоднозначные и оборванные пути, ограничение обхода,
коллизии сокращений, match и контракт prompt/cap в ремонтном раунде.

Первый live `20261111-124829-search-v2-compact`: 5/6 верных; одно требование
компактности при старых форматированных примерах не всегда соблюдалось.
0033 получил неверный match и отказ в ремонте.

После компактирования примеров и уточнения get/match:
`experiments/runs/20261111-124950-search-v2-compact-fixed` (3 повтора):

| Задача | Verified | Вызовы | Стоимость |
|---|---:|---|---|
| search_0034 | 3/3 | 1, 1, 1 | 309.5 каждый раз |
| search_0033 | 2/3 | 1, 1, 2 | 150.7, 150.7, 181.1 |

0034: 14 операций, 635 input + 246 output. V1 при достаточном капе:
634 input + 360 output = 423.4 экв. Снижение полной стоимости ~27%.
0033: в третьем повторе модель написала find(name="cap") вместо get по ссылке;
executor не нашёл ответ, QA вернул Wood вместо Chomptrick. Это нерешённая
семантическая ошибка, а не ошибка оценки глубины. V2 пока экспериментальная.

## Адаптивный cap: live-проверка

Полное сравнение на 27 задачах × 3 повтора: [CAP_COMPARISON.md](CAP_COMPARISON.md).
Переключатель `SEARCH_V2_CAP_MODE=static` выбирает фиксированный стартовый cap
400; default `dynamic` — рекомендацию complexity. Ручной max_tokens имеет
приоритет. Бюджетный гейт действует в обоих режимах.

Серия `20261111-131622-search-v2-adaptive-cap`, 3 повтора:
0034 — 3/3, output=246, requested=352, allowed=349 (envelope=420),
309.5 экв.; 0033 — 1/3, requested=160, output=93/149/113. Усечений нет.
Контроль `20261111-131940-search-v2-fixed-cap-control` с override=400:
0034 — 3/3, также allowed=349 после бюджетного гейта; 0033 — 2/3.
Ошибки 0033 семантические (find по имени переменной), есть в обоих режимах;
выборки малы, равенство качества не доказано. Уменьшение cap само по себе
не снижает стоимость законченного ответа. Оба контроля выполнялись в sandbox.

```bash
.venv/bin/python -m solutions.search.v2.complexity --only search_0033 search_0034
.venv/bin/python experiments/run_experiment.py --label search-v2 --only search_0033,search_0034 --versions search=v2 --model qwen3.8-27b-noreason --budget 2000
```
