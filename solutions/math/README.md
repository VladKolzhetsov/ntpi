# Math-солверы

Решение задач типа `math` (текстовые арифметические задачи, проверка
`exact_int`) версионным набором солверов. Методология версионирования:
v1 всегда «в лоб» (бейзлайн), следующие версии сравниваются с ним по
точности и стоимости; уроки версии фиксируются до перехода к следующей.

Контракт всех версий одинаков (`solutions/base.py`):

```python
solve(task: Task, client: LLMClient, model: str) -> SolveResult
# SolveResult: task_id, status (answered | failed), answer,
#              written (обе позиции answer.txt), cost, trace
```

## Таблица версий (живой прогон на тренировке math_0000/math_0004)

| Версия | Модель | Точность | Стоимость | Статус |
|---|---|---|---|---|
| v1 «в лоб», кап 400 | noreason | 0/2 | 27–424 экв. | бейзлайн |
| v1 «в лоб», кап 800 | noreason | 1/2 | ~527 экв. | зонд |
| v1 «в лоб», кап 400 | reason | 2/2 | 248–355 экв. | бейзлайн |
| **v2 код-планировщик** | **noreason** | **2/2 (round0)** | **47–79 экв.** | **текущая** |

Эквивалент = `completion_tokens + prompt_tokens / 10`.

---

## v1 — «в лоб»

`solutions/math/v1/solver.py`. Один вызов LLM: промпт = полная инструкция
задачи + просьба закончить строкой `Answer: <значение>`. Извлечение ответа
детерминированное (`_extract`): последний маркер `Answer:` (модель может
пересчитывать), иначе последняя непустая строка; для `exact_int` — чистка
пробелов и запятых («1,735» → 1735), для `exact_str` — фенсы/кавычки/
замыкающая точка. Нет ответа → файл не создаём.

### Уроки v1

- **noreason двоичен**: либо отвечает одной строкой без рассуждения —
  и ошибается в арифметике (math_0004: 1450 вместо 1735, всего 27 экв.),
  либо рассуждает развёрнуто — и упирается в токен-кап
  (math_0000: верный 389, но `finish_reason=length`, 424 экв. потрачено).
- Инструкция задач содержит «Compute it with the bash tool (python3 -c)» —
  модель **следует инструкции, а не промпту**: пишет python-верификацию,
  оборачивает код в bash-команды. Это уводит токены в «верификацию»
  вместо ответа.
- reason-модель решает (2/2), но ~90% её цены — скрытые reasoning-токены
  (~330 из 354.8 экв.): арифметика «в голове» — самый дорогой способ
  считать.

## v2 — код-планировщик (текущая)

`solutions/math/v2/solver.py`. Арифметика перенесена из модели в
детерминированный python; LLM платит только за трансляцию задачи в код.

```
instruction ──► [LLM: python-программа]     1 вызов, noreason, temp 0
                   │                          (языковая задача — CoT не нужен)
                   ▼
              _extract_code                фенсы → голый print( →
                   │                        снятие bash/python3 -c обёртки
                   ▼
              python3 -c <код>             сабпроцесс, таймаут 10с
                   │
                   ▼
              последний print              для exact_int — чистка пробелов/
                   │                        запятых; фенсы/кавычки/точка
                   ▼
              answer.txt                   ОБЕ позиции; провал → файла нет
```

Ошибка исполнения (stderr, ненулевой exit, таймаут) → **один ремонтный
раунд**: модель видит свой код и текст ошибки, отвечает исправленной
программой. Двойной провал → `status=failed`, файл не создаём.

## Детекция нерешаемости (v2)

15–25% задач по регламенту нерешаемы; пишущих их генераторов ловим
тремя уровнями — от детерминированного к вероятностному:

| Уровень | Механизм | Цена | Что ловит |
|---|---|---|---|
| 0. `detectors.py` | детерминированные фильтры **до** LLM | 0 токенов | подмену сущности («условие про boxes, вопрос про crates») |
| 1. маркер `UNSOLVABLE` | в том же вызове, что и программа | 0 доп. вызовов | нехватку/противоречивость данных — общий случай |
| 2. рантайм | NameError/ZeroDivisionError + ремонт | уже оплачено | «честные» отказы моделей |

`detectors.py` — каждый фильтр отдельная функция
`(instruction) -> reason | None`, реестр `DETECTORS`; **отключение =
убрать функцию из списка**, правок солвера не нужно. Сейчас один фильтр:

- **noun-guard** (`question_noun_absent`): вопрос = последнее предложение
  с `?`; если в нём есть содержательные слова (не стоп-слова how/end/
  total/…) и **ни одно** не встречается в условии (наивный стемминг
  s/ies, алиасы единиц km/kilometer, допуск хвоста ≤ 2) → задача
  нерешаема, LLM не вызывается.

Фильтр консервативен дважды: служебные слова не сущности; приманка-
существительное в вопросе («warehouse») пропускает задачу — ловушку
добивает маркер. Идея «разложить вопрос семантикой и понять, хватает ли
вводных» в общем случае = детерминированный солver (нужно построить
solution DAG, т.е. решить задачу) — поэтому общий случай отдан маркеру.

Маркер `UNSOLVABLE` в промпте: «If the problem cannot be solved because
required data is missing or contradictory, reply with exactly:
UNSOLVABLE». Принимается в любом раунде (первая строка = маркер,
короткое пояснение допускается); ответ, содержащий `print(` — код,
не отказ. Отказ → `status=unanswerable`, answer.txt не создаётся.

### Почему это дешевле

- Перевод словесной задачи в код — **языковая** задача: noreason
  справляется, скрытых reasoning-токенов нет вовсе.
- Арифметика исполняется питоном точно — та точность v1-reason,
  но в 4–5 раза дешевле.
- Модель по этой инструкции *естественно* пишет python — харнесс
  исполняет то, что модель и так производит.

### Грабли, закрытые в v2

| Грабли | Проявление | Закрытие |
|---|---|---|
| bash-обёртка `python3 -c "…"` | SyntaxError → лишний ремонт (+120 экв.) | запрет в промпте + `_unwrap_shell` (ast.literal_eval → парные кавычки) |
| отладочные принты | несколько чисел в stdout | берём последний непустой print |
| «1,735 boxes» в stdout | ответ не парсится как int | чистка пробелов/запятых до regex |
| вечный цикл в коде | suite зависает | таймаут 10с → ремонт → сдача |
| недетерминизм прокси | тот же temp 0 → разные ответы | нормализация на нашей стороне, ремонтный раунд |
| stdout `270.0` при exact_int | «последнее целое» рвало float на «270» и «0» → ответ `'0'` | `_NUM_RE` (число с дробной частью = одно число); целое в float-записи → int, нецелый float сохраняем |
| отказ ВНУТРИ программы | `print("UNSOLVABLE")` не распознан → ремонт → failed за ~404 экв. | маркер ищется и в stdout; маркер не принимается за ответ (exact_str) |
| question-only ложные срабатывания | noun-guard валил самодостаточные вопросы (0015/0016/0038) | фильтр пропускает задачи без условия до вопроса (`start == 0`) |
| болтливость вместо кода | 7/143 первых вызовов жгут кап 400 рассуждениями в комментариях без единого `print()` → решаемые задачи (math_0010) падают за ~446 экв. | усечение детектируется (`completion >= cap` и кода нет) → ремонт без эха болтовни, кап 250, «program ONLY» (см. ниже) |

### Защита от болтливости (2026-11-12)

Живая статистика по 143 первым вызовам math: **7 (4.9%) упёрлись в кап 400,
не написав ни одного `print()`** — и это всегда потеря (задачи `0043`, `0045`,
`0055`, `0010`). Цена события — весь кап (400) + испорченная задача.

Что показал разбор ремонтов после такого усечения (6 случаев): **полезен 1 из
6** (0055 дал код, но неверный; 2 вернули `UNSOLVABLE` — верно для нерешаемых;
2 отрезаны бюджетом; 1 без файла). Значит ремонт сам по себе не спасение —
спасает то, что он **дешёвый и предметный**.

Механика (`solutions/math/v2/solver.py`):

1. Ответ считается «болтовнёй», если кода нет **И** `completion_tokens >= cap`
   (усечение). Обрезанный код (есть `print(`, но синтаксис рвётся) сюда НЕ
   попадает — это обычный ремонт с разбором ошибки.
2. Для болтовни ремонт идёт по другому шаблону: эхо урезано до 400 символов
   (болтовня — шум, а не контекст), `max_tokens=250` вместо 400 (программа
   короткая), формулировка жёсткая: «cut off at the token limit … program
   ONLY … no comments … start with the code».
3. Если и второй раз болтовня — сдаёмся (третьего вызова нет), потеря
   ограничена ~250 вместо ~400.

Первый кап оставлен 400: здоровые ответы доходят до **392 токенов** (данные
143 вызовов, `p95`), понижение до 250 отрезало бы ~15% корректных программ.
`cost_worst` не изменился: худший путь (обычный ремонт с эхом и капом 400)
по-прежнему учтён, а ветка усечения строго дешевле — граница остаётся
верхней.

### Корень: комментарии вместо кода (2026-11-12)

Детектор усечения лечит симптом. Диагностика причины: **64% всех символов
ответов math — это `#`-комментарии**, в которых модель ведёт алгебру.
У задач-«болтунов» они съедали 223–344 из 400 токенов. Пример (`0043`):
модель аккуратно вывела «дискриминант отрицательный, вещественных корней
нет… it might be unsolvable» — то есть **решила задачу** — но кап кончился
раньше, чем она написала `print("UNSOLVABLE")`. Верный вывод остался в
комментарии.

Промпт-фикс: вместо мягкого «no comments explaining the reasoning»
(модель читает как «объясняй кратко») — жёсткий и подкреплённый примером:

```
Output the code FIRST: the reply must start with a Python statement …
Write NO comments at all - no '#' lines, no reasoning in prose …
Example: n = 1752\nn = n // 2\nprint(n).
```

Живой замер (те же 12 задач, `math-nocomments`):

| Метрика | до (ramble-fix-r2) | после (nocomments) |
|---|---|---|
| баллы | 32/42 | 32/42 |
| расход | 2191.3 экв. | **1508.3 экв. (−31%)** |
| медиана | 162.9 | **95.3** |
| `0043` | failed 442.7 | **unanswerable 331.7** |
| упёрлись в кап 400 | 1 | **0** |
| completion-хвост | 257/299/400 | 101/175/285 |

`0043` давала 396–489 экв. и падала пять прогонов подряд; теперь маркер
`UNSOLVABLE` за 331.7. Комментарии не исчезли полностью (64% → 48%), но
перестали вытеснять код. `cost_worst` после смены промпта перепроверен:
**180 задача-прогонов, 0 нарушений**.

Урок: промпт-инструкция «не объясняй» не работает, пока она мягкая; работает
прямая директива о форме вывода + пример. И чинить надо не бюджет, а то,
за что модель платит токены.

## cost_worst: граница стоимости (2026-11-12)

`solutions/math/v2/complexity.py` публикует `cost_worst(task) -> float` —
контракт раннера (`RunConfig.worst_case`/`--worst-case`): плотность задачи
считается как `reward / cost_worst`, envelope = сама граница.

Лестница math/v2 проще поисковой, поэтому граница точная, без калибровок:

```
solve() = фильтры (0 токенов) -> ВЫЗОВ 1 -> максимум ОДИН ремонтный ВЫЗОВ 2
fallback отсутствует
cost_worst = C1 + C2
  C1 = input/10 + cap                       (completion <= max_tokens: API)
  C2 = (input + echo + 60)/10 + cap          (эхо ответа: text[:2000])
  echo = min(cap, 500)                       (эхо не может превысить cap)
```

Единственное приближение — оценка input по символам
(`60.289 + 0.236765 × chars`, OLS из search/v2/tokens). Перенос модели на
math даёт MAPE 23.8%, но input — это ~3.5% от границы, так что ошибка
оценки даёт ≤4% к `cost_worst`; output-кап — точный максимум, заданный нами.

**Валидация** против 72 сохранённых задача-прогонов математики: **0
нарушений** (факт ≤ границы), медиана использования границы **7.6%**,
максимум **53%** — запас двукратный, что объяснимо: граница предполагает
полный кап на обоих вызовах, а медианный completion ~40 токенов.

Никаких вероятностей и переноса калибровки: `cost_worst` — верхняя граница
при достаточном бюджете, а не ожидание. `expected`/`reward` не читаются.

**Важный эффект на триаж** (A/B на 12 задачах, 2026-11-12): граница math
(922–954) в 11 раз выше прежнего `EXPECTED_COST=80`, поэтому в режиме
`--worst-case` плотность math падает до `reward/922 ≈ 0.005` против
`reward/140 ≈ 0.036` у search — math становится в ~6.5 раз менее
приоритетной. При бюджете 5000 экв. и 100 задачах это может отрезать
math раньше.

**Чистый A/B (51 задача × 2 повтора × 2 режима, 2026-11-12).** Первый A/B
на 12 задачах × 1 повтор показал «worst-case хуже» (−5 баллов, +19% экв.)
— это был шум прокси (флип `0055`). Повтор на всей выборке с фиксом
анти-болтливости, бюджет 15000 (без скипов):

| Метрика | default | worst-case |
|---|---|---|
| баллы (оба повтора) | 110, 110 | 110, 110 |
| расход (повторы) | 4842, 5800 | 5635, 5116 |
| медиана расхода | 5321 | 5375 (+1%) |
| упоров в кап | 2 | 2 |
| отрезано ремонтов (envelope 240) | 3 | 0 |

Выводы: **баллы идентичны, расход +1% — глубоко внутри шума повторов**
(собственный разброс серии ±10–20%). Envelope-эффект работает как
задумано: default отрезал 3 ремонта на безнадёжных задачах
(`0043/0047/0056` в r2) и сэкономил ~350 экв., worst-case дал им
дописаться — и заплатил, но в общем тотале это утонуло. Прокси в
основном детерминирован: 28/51 задач побайтно-стабильны по стоимости,
вариация сконцентрирована на нерешаемых (модель раздумывает).

Инструмент: `experiments/ab_report.py` (default-серия, worst-серия) —
медианы по повторам, per-task дельты, классификация «сист./шум»
(систематика = все повторы согласны по направлению).

Флаг остаётся выключенным по умолчанию — не из-за риска для math, а из-за
кросс-типового триажа: пока `cost_worst` публикует только math, его
плотность уходит вниз против типов с `EXPECTED_COST`. Включать — когда
все четыре типа опубликуют границы.

### Откаченный эксперимент: мягкий гейт на ремонт (2026-11-12)

Гипотеза была: envelope = граница (954 при медиане 80) не ограничивает
задачу, а снимает ограничение — значит нужен `soft_limit = k × EXPECTED_COST`,
запрещающий углубление. Реализовано (`ScopedBudget(soft_limit=...)`,
`SOFT_GATE_FACTOR`), замерено и **откачено**:

| Что показал живой прогон | Факт |
|---|---|
| сбойный ремонт `0055` отрезан | да: 651 → 160 экв. |
| решаемая `math_0010` доведена до FAIL | да: 446 экв. впустую (обычно 86–151 ✓) |
| `math_0043` (дорогая нерешаемая) | 442 экв., ремонт отрезан |

Причина провала: гейт бьёт **после** первого вызова, а ущерб наносится
**на** нём. Первый вызов капнут (400), и если он ушёл в болтовню —
задача уже потеряна; запрет ремонта лишь не даёт её вытащить, а
оказываются под ударом именно **обычно решаемые** задачи (у нерешаемых
и так маркер). Корень лечится не бюджетом, а усечением ответа
(раздел «Защита от болтливости»). Механизм `soft_limit` оставлен в
`ScopedBudget` выключенным — включать только осознанно.
`SOFT_GATE_FACTOR` сохранён для справки.

Мораль: **бюджетный гейт — не замена работе с качеством ответа.** Экономия,
построенная на «не дать потратить», отбирает баллы у тех, кто ещё
спасаем; экономию даёт «потратить меньше на неудачу».

CLI для просмотра (офлайн, без LLM):

```bash
.venv/bin/python -m solutions.math.v2.complexity --only math_0055
```

Тесты: `solutions/math/test_v2_cost_worst.py` (12) — разложение формулы,
инварианты, монотонность по длине инструкции, контракт раннера, реакция на
`MAX_REPAIRS=0`.
