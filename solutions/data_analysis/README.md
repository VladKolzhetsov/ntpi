# data_analysis — версионирование солверов

Задача типа: в `workspace/` лежит CSV, инструкция объявляет схему и
спрашивает агрегацию/фильтр («How many units of product 'widget' were
sold in months 7 through 8?»). Методология общая: v1 «в лоб» — базовая
линия, следующие версии обязаны быть точнее и/или дешевле; уроки
фиксируются до перехода к следующей версии.

## Классы проблем (и где они решаются)

| Проблема | Дом | Цена |
|---|---|---|
| Огромный CSV | сама архитектура v2: данные НЕ в контексте, только profile | ~0 |
| Колонки в условии ≠ колонкам в файле (ловушка) | `precheck.py`: детекторы ДО LLM | 0 токенов |
| nan в колонках | `nulls N/M` прямо в profile + политика в промпте v2 (skip, не fillna(0)) | ~30 ток. промпта |
| Много nan → падают операции | то же: программа пишет `sum(... if x)` | 0 |
| Файла нет / имя врёт | `find_csv_path` (толерантно) + детектор `csv_file_missing` | 0 |
| SUM vs COUNT vs AVG (семантика) | подсказка соответствия в промпте v2 | ~40 ток. |
| Пустой результат фильтра (0) | НЕ детектируем — это ответ, а не отказ | 0 |

## precheck.py (общий для версий)

Детерминированный разбор до LLM, 0 токенов. Три источника:

```
инструкция -> имя файла + декларация колонок ("has columns a,b,c (20 rows)")
CSV-файл    -> заголовок (Sniffer: , ; \t |, utf-8-sig) + profile колонок
вопрос      -> упоминания колонок (word-boundary + стемминг, solutions/text.py)
```

Порядок авторитетов: **файл (факты) > декларация инструкции (подсказка)**.
Колонка есть в файле, но не в декларации — норма; колонка объявлена,
отсутствует в файле И о ней спрашивают — unanswerable (детектор
`declared_column_absent`; декларация вырезается из текста вопроса,
иначе колонка «упоминала бы себя»).

Profile (потоковый, O(памяти) от колонок, не строк; кап 200k строк):

```
month: int; nulls 0/300; range 1..12
product: text; nulls 0/300; 4 unique: gadget, gizmo, sprocket, widget
```

Реестр `DETECTORS = [csv_file_missing, declared_column_absent]`;
отключение = убрать из списка или передать свой в `precheck()`.

Сознательный пробел: слово вопроса, не похожее ни на одну колонку
(«average revenue»), отказом не считается — это может быть вычисляемая
величина; решает LLM (маркер UNSOLVABLE). Полная проверка «хватает ли
данных» = решение задачи = детерминированный солвер без LLM.

## Версии

### v1 «в лоб» (`v1/solver.py`)

Инструкция + вся таблица в контексте (капы 400 строк / 20k символов)
→ один вызов LLM → `Answer: <значение>` → чистка по check → answer.txt.
Precheck-гейт работает и здесь: сломанные задачи не доходят до LLM.

Живой прогон на тренировке (noreason, temp 0):

| Задача | Кап 500 | Кап 1500 |
|---|---|---|
| data_analysis_0002 (20 строк) | ✓ 158, 345.9 экв. | — |
| data_analysis_0006 (300 строк) | ✗ провал, 1007.6 экв. | ✓ 284, 1090.6 экв. |

Уроки v1:
- модель читает таблицу «глазами» и **перечисляет подходящие строки
  по одной** → output-токены растут как O(строк): на 300 строках
  перечисление оборвалось на капе 500 ДО строки Answer — 1008 экв.
  потрачено, файла нет, тихий провал;
- точность «в лоб» растёт только с капом, т.е. ещё дороже: 1090 экв.
  за одну задачу — в 5 раз дороже v2;
- 20-строчная таблица — предел разумности для «глазами».

### v2 код-планировщик (`v2/solver.py`)

Таблица НЕ в контексте. Промпт = инструкция + имя файла + заголовок +
profile (~15 ток./колонку) → короткая python-программа (csv-модуль)
→ исполнение в сабпроцессе **с cwd=workspace** (код открывает файл по
относительному имени, как велит инструкция «work only inside the
current directory») → последний print → чистка по check.

Стоимость НЕ зависит от размера файла (тест на 1000 строк: промпт
< 1200 символов). Ремонт — 1 раунд по stderr, как в math/v2.
nan-политика в промпте: пропускать, не заполнять нулями. Маркер
UNSOLVABLE — тот же контракт, что в math/v2.

Живой прогон (3 прогона, noreason, temp 0): **2/2 в каждом (round0)**:

| Задача | Ответ | Стоимость (разброс прогонов) |
|---|---|---|
| data_analysis_0002 | ✓ 158 | 188–408 экв. |
| data_analysis_0006 | ✓ 284 | 202–237 экв. |

Разброс — недетерминизм прокси при temp 0 (длина ответа варьируется),
не наша логика. Один ранний прогон упал «no code» ×2: сообщение
ремонта «no python code in the reply» было неточным (программа может
быть, но без print()) — уточнено на «the reply contains no Python
program that prints the answer» в обоих код-солверах; после этого
сбоев не наблюдалось. При рецидиве — кандидат на эвристику
«код без print → исполнить и отремонтировать по пустому stdout».

Итоговая таблица:

| Версия | Точность | Стоимость |
|---|---|---|
| v1 «в лоб», кап 500 | 1/2 | 346–1008 экв. |
| v1 «в лоб», кап 1500 | 2/2 | 1090.6 экв. (300 строк) |
| **v2 код-планировщик** | **2/2 (round0)** | **188–222 экв.** |

## Общие модули, выкачанные при этом типе

- `solutions/text.py` — `words/stem/stems_match` (общие для math-детекторов
  и DA-precheck);
- `solutions/pyrun.py` — извлечение кода из ответа (фенсы, `python3 -c`
  обёртки), сабпроцесс-раннер с cwd, чистка stdout (общий для math/v2 и
  DA/v2);
- `solutions/base.py::extract_answer` — чистка «Answer:»-ответов v1
  (общая для math/v1 и DA/v1).

## Adversarial-пакет (2026-11-12)

12 ловушек (`tasks/make_da_adversarial.py`, задачи 0034–0045), каждая
`expected` пересчитана независимым кодом и сверена assert'ом до записи.
Живой прогон DA/v2: **10/12 решаемых верно + 2/2 нерешаемых отсечено
precheck'ом за 0 токенов**, единственный сбой — ловушка 0036.

| id | Ловушка | Исход |
|---|---|---|
| 0034 | nan в суммируемой колонке | ✓ 22 |
| 0035 | регистр значения ('Widget'/'WIDGET') | ✓ 15 |
| 0036 | разделитель ';' | ✗ → **исправлено** |
| 0037 | join двух файлов (orders + customers) | ✓ 17 |
| 0038 | second highest DISTINCT | ✓ 25 |
| 0039 | «in whole dollars» при дробной сумме | ✓ 36 |
| 0040 | колонка объявлена, в файле нет | отсечено, 0 ток. |
| 0041 | месяц словом ('March') | ✓ 12 |
| 0042 | колонка целиком пустая | ✓ 0 |
| 0043 | границы диапазона (7 through 8) | ✓ 33 |
| 0044 | нет CSV вообще | отсечено, 0 ток. |
| 0045 | процент + точность (exact_str) | ✓ 20.0 |

**Урок 0036 (дефект харнесса)**: precheck знает разделитель (Sniffer
его уже определил для profile), но промпт его не сообщал. На файле с
';' модель писала корректную программу с дефолтной ',' → `KeyError` →
ремонт «чинил» его в уверенно неверный ответ `'0'` — тихий провал без
крэша, худший класс сбоев. Фикс: `build_user_prompt` раскрывает
разделитель (`CSV file: sales.csv (delimiter ';')`), для запятой —
примечание не добавляется. Живой фикс: 261.2 экв. (ремонт + неверный
ответ) → 127.4 экв. (round0, верно). Промпт вырос только у нестандартных
диалектов (~16 символов), побайтовое совпадение с complexity — в тесте.

## cost_worst (`v2/complexity.py`, 2026-11-12)

Граница расхода DA/v2 на задачу, 0 токенов, детерминированно. В отличие
от math/v2, input не оценивается, а **восстанавливается точно**:
user-промпт целиком строится из файла задачи (`build_user_prompt`), и
complexity использует ту же функцию. Единственное приближение — перевод
символов в токены (OLS из search/v2/tokens), это ~4% границы.

```
precheck не прошёл (нет файла / нет колонки) -> 0.0   # LLM не звали
C1 = input/10 + cap                                 # cap = MAX_TOKENS=600
C2 = (input + echo + error)/10 + cap                # echo = min(cap, 500)
cost_worst = C1 + C2                                # MAX_REPAIRS=1
```

Инвариант «факт ≤ границы» проверен на всех сохранённых прогонах
(35 задача-прогонов, включая adversarial): **0 нарушений**; медианное
использование границы 10.5%, p90 14.2%, max 19.4%. Граница честная
(не раздута на порядок), но с запасом ~5× — доминирует удвоенный
output-кап (600+600), а не input. Сравнение с типовым профилем раннера:
EXPECTED_COST[data_analysis]=260 против cost_worst≈1345 — envelope
в `--worst-case` станет в ~5 раз щедрее, что и видно на math A/B.
